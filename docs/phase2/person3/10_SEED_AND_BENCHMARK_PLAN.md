## 1. Objectives

1. Produce deterministic, FK-valid data, large enough to expose index behaviour (RQ-A06: ≥70,000 rows in the demonstration tables).
2. Measure baseline and optimised configurations reproducibly, with Actual Execution Plans and STATISTICS IO/TIME (RQ-A05; S-07 method; S-15 lecturer guidance).
3. Prove that optimisations do not change results.

## 3. Seed data plan

### 3.1 Principles

1. **Deterministic:** pseudo-random values come from a hash of (seed, stream name, row number), so the same seed gives identical data. Unseeded sources (`NEWID()`, `RAND()` without a seed) are not used for data values.
   **Time:** generated IssuedAt and PaidAt values are UTC (D-014); business hours, days and month boundaries are generated in Asia/Ho_Chi_Minh time and converted, and boundary rows include payments between 00:00 and 06:59 local time on the 1st.
2. **Set-based T-SQL** (TECHNICAL_RECOMMENDATION, D-022). There are no extra dependencies: Python is present but has no database driver, and installing one is not authorized. Row numbers come from `GENERATE_SERIES` (needs compatibility level ≥ 160; verify) or a tally CTE.
3. **FK-valid by construction:** parents are generated first and children pick existing parent keys. All constraints stay enabled and trusted.
4. **Derived data is computed, never invented:** MEMBER_MONTHLY_SPENDING, PointsEarned, CurrentPoints, Tier_ID and any summary are aggregated from the generated PAID invoices using the approved rules (D-006, D-007, D-008, D-013). Otherwise reconciliation tests would fail by design.
5. **Parameterised:** all sizes and distributions live in one configuration block or table that is recorded in the manifest.
6. **Shared tables (revised 2026-11-08, D-027):** BRANCH, EMPLOYEE, MEMBER, MEMBER_TIER, SERVICE_PLAN and PRODUCT are shared dependencies; BRANCH_INVENTORY and every other non-P3 table are out of scope and are **not generated by P3**. P3 generates data for its four tables only. Shared parents are the TEST_ONLY key fixtures of D-026 (F001) with **key rows only** (§3.4: 12 branches, 30,000 members, employee, plan and product keys); no names, prices, stock, assignments, statuses or other attributes of other members' domains. Line prices come from a deterministic per-key price list in the seed configuration (TEST_ONLY; [12 §2b](12_INTEGRATION_PLAN.md#2b-dependency-register-interim-assumptions-until-p6) DEP-04). MEMBER's loyalty columns (`CurrentPoints`, `Tier_ID`) and MEMBER_TIER rows exist only through the F002 fixture extension, created by the first approved WO that needs them (DEP-02, DEP-03; WO-P3-P1-01 §3.3a rule 4). No other member's workflow is simulated: no stock movement, no entitlement activation, no PT sessions, so `ValidFrom`, `ValidUntil` and `PTSessionsRemaining` stay NULL (DEP-06). No P3 implementation of another member's table is built; fixtures are replaced by the team schema at P6 and the validation is re-run.
7. **Logical consistency of the P3 data:** header totals equal the sum of the lines (D-023, V-TOT); payment states follow D-005 (PAID rows have `PaidAt ≥ IssuedAt` and a method; PENDING and CANCELLED rows have no `PaidAt`); every member, branch, employee, plan and product reference is a fixture key (FKs enabled and trusted); MEMBER_MONTHLY_SPENDING is aggregated from the PAID invoices only, by the Asia/Ho_Chi_Minh month of `PaidAt` (D-013), with `PointsEarned` per D-006.

### 3.2 Generation order

Revised 2026-11-08 (D-027): only P3 tables are generated; shared parents are TEST_ONLY key rows.

1. TEST_ONLY fixture key rows (F001): BRANCH, EMPLOYEE, MEMBER, SERVICE_PLAN, PRODUCT, keys only.
2. INVOICE headers (IssuedAt in UTC from local business hours; member, branch, employee keys by the configured distributions).
3. INVOICE_SERVICE_ITEM and INVOICE_PRODUCT_ITEM (prices from the seed price list; `ValidFrom`, `ValidUntil`, `PTSessionsRemaining` NULL).
4. Header totals from the lines (D-023).
5. Status, `PaidAt` and method (D-005; status mix of §3.4).
6. MEMBER_MONTHLY_SPENDING aggregated from the PAID invoices (D-013; `PointsEarned` per D-006).
7. _Only if F002 is in scope:_ MEMBER_TIER fixture rows (D-008 values), `MEMBER.CurrentPoints` (D-006, D-024) and `MEMBER.Tier_ID` evaluated as of the dataset end date (D-007, D-008).
8. Validation (§3.5). Statistics are updated WITH FULLSCAN by WO-P3-P2-02 per configuration (§4.3 step 2), not by the generator.

Removed from P3 on 2026-11-08: EMPLOYEE assignment, MEMBER_TIER and MEMBER attributes outside F002, SERVICE_PLAN and PRODUCT attributes, BRANCH_INVENTORY. The revenue summary (D-015) is built in WO-P3-P4-02, not in the seed.

### 4.3 Measurement protocol

1. Bring the database to the dataset snapshot for the configuration (restore, or rebuild and verify the checksum).
2. Apply the configuration (B0, B1-IX-xx, …). Update statistics WITH FULLSCAN on the affected tables.
3. Set the plan-cache policy, either the routine's documented `OPTION (RECOMPILE)` or a database-scoped procedure-cache clear before the configuration, and record it.
4. **Warm-up:** run each query/parameter set once and discard the result.
5. **Timed runs:** N = 15 runs per query × parameter set (N ≥ 20 when p95 is reported), in a fixed interleaved order, **without** actual-plan capture (plan capture adds overhead). Capture `SET STATISTICS IO, TIME ON` output and the client-side elapsed time.
6. **Plan capture:** one separate execution with the Actual Execution Plan, saved as `.sqlplan` plus a screenshot.
7. **Cold-cache variant (optional):** only on a dedicated, non-shared instance with sysadmin rights: `CHECKPOINT` + `DBCC DROPCLEANBUFFERS` before each run, labelled "cold". Warm results are the primary comparison because the working set fits in memory ([04 §4](04_WORKLOAD_AND_DATA_VOLUME.md#4-rough-storage-estimate-assumption_pending_approval-verify-with-sp_spaceused-after-seeding)).
8. If the environment changes during a series (other load, power plan, restart), discard the series and rerun it.

### 4.4 Metrics and statistics

| Metric | Source | Reported as |
|---|---|---|
| Logical reads (per table and total) | STATISTICS IO | Median (deterministic for a given plan) |
| CPU time | STATISTICS TIME | Median, IQR |
| Elapsed time (server and client) | STATISTICS TIME, client timer | Median, IQR, min, max; p95 when N ≥ 20 |
| Rows returned; estimated vs actual rows | Plan | Per configuration |
| Plan shape | Actual plan | Operators: scan/seek, lookup, aggregate, sort, parallelism, partitions accessed |
| Index/summary size | `sys.dm_db_partition_stats` | Pages, MB |

### 4.5 Write-overhead measurement

- Prepare K = 1,000 PENDING invoices in DS-L (deterministic).
- Settle them one transaction per call through the harness, with and without the candidate index or summary.
- Record per-call elapsed (median, p95), total CPU and the change in index size. Under the same protocol, also measure the insert cost of F05-like invoice creation.
- Restore the snapshot between the compared runs.

### 4.6 Correctness comparison

Each query × parameter set produces a **result hash**: SHA-256 over the result rows in a defined order, with decimals in a fixed format. Configurations of the same query must produce identical hashes (T-REG-01, T-REG-02). Unordered checksums are not used for this purpose because of collision risk.

## 5. Honesty rules

1. Report templates show `NOT YET MEASURED` until a RUN_ID exists.
2. Estimates (e.g. [04 §4](04_WORKLOAD_AND_DATA_VOLUME.md#4-rough-storage-estimate-assumption_pending_approval-verify-with-sp_spaceused-after-seeding)) are labelled ESTIMATE and never mixed into measured tables.
3. Runs that contradict the hypothesis are kept and reported.
4. Improvements are stated with their configuration, dataset and RUN_ID, e.g. "logical reads 3,400 → 25 (DS-L, B0 → B1-IX01, RUN_ID …)". Never as an unqualified "X% faster".
5. AI-generated expectations (S-09, this plan) are hypotheses, not findings.
